# Pages and fragments with htmx

Read `references/patterns.md` for code. These rules apply to every UI change.

## Routes and templates

- One route module per area in `app/api/`. A route returns a full page for normal requests and only the fragment when `HX-Request: true` (use the shared `render()` helper).
- Templates: `app/templates/pages/<area>.html` extend `base.html`; fragments live in `app/templates/fragments/<area>/_<name>.html` and never extend anything.
- Routes call services only. No SQL, no providers, no business rules in routes or templates.
- Every non-page request carries the launch token through `hx-headers` on `<body>`; never remove it or add a route that skips the token middleware.
- Page routes are registered directly on the app through `register_pages` (app/api/pages.py), or with `app.add_api_route(..., methods=["GET", "HEAD"], tags=[PAGE_TAG])` as the inbox, job and company areas do, never through an included router; every other route needs the token. GET routes never have side effects (spec 2.9 rule 12).
- **Token-free page routes with an id** (`/facts/{id}/edit`, `/jobs/{id}`, `/companies/{id}`; ADR-094, ADR-098, ADR-100): the page loads without the token and without `HX-Request`, reads only, and checks the id with `is_safe_id` (one path segment of the safe shape) before any lookup. An unsafe or unknown id answers the fixed plain-text 404 that echoes nothing (`JobNotFound.message`; "This company wasn't found."). Anything that changes data, and every part of the page that is loaded as a fragment, is a separate token-protected route; POST routes also check the origin. A new page with an id needs a seeded id in `test_every_page_path_dispatches_to_its_page_without_token` and in the page map of `tests/leak_scan.py`, a fixed-404 test, and a line in spec 2.9 rule 12 (a page shows stored data to any local process; rule 13). In templates, link to an id only if it passes `is_safe_id` (a Jinja global) and show any other id as plain text.
- **Filter, sort and group-by forms push the page address** (ADR-099 item 2). Such a form is a plain `GET` form to the page (`/inbox`), so it works without JavaScript and a filtered address can be reloaded, bookmarked and used with Back. htmx enhances it by fetching the fragment route (`/inbox/queue`), and the fragment answer sets `HX-Push-Url` to the page address with the validated query values (a hidden `push=1` asks for it); links that change the view use `hx-push-url` with the page address. Never push a fragment route: reloading it answers 403. The server validates the query values (a bad value is dropped, never echoed), and a GET with filters writes nothing. Keep the filter values in the links and forms of the screen, so a triage action or Undo returns to the same filtered list. Under Saves below, "never use `HX-Push-Url` for a settings save" still holds: only a read-only view change pushes.

- **Steps and lazy blocks on a token-free page** (M6; ADR-112, ADR-114, ADR-115): a multi-step screen is one token-free page read with its step in the query (`?tab=tailoring&step=N`), whose resume step is derived and whose GETs write nothing. Each step is a protected fragment (`/applications/{id}/tailoring/{step}`) under `fragments/tailoring/`. Each POST carries the version it changes, checks the origin, and answers with the exact version it committed. A block that holds personal data (the contact block, the letter frame) is a placeholder on the page that loads its protected fragment with `hx-trigger="load"`; the page itself never holds the value.

## Interaction rules

- After every swap that changes what the user is working on, move focus deliberately (the swapped region's heading or first control) and announce the result in the global `aria-live` region.
- Every drag-and-drop has a keyboard alternative. Board uses status menus with shared behavior (`status-menu.js`) on cards and in the drawer (table rows open the drawer): Enter opens it, arrows move, Enter submits, Escape returns focus. Menu and Sortable (`board.js`, loaded only by Board) post to `/applications/{id}/status` with `version`, `status` and `source=menu|board`; the server records drawer moves as `source=drawer` when the target is the application detail. A drop posts from the new position; a refusal or request error restores the original position, and the server response is authoritative. Destroy Sortable instances before swaps, disable dragging at phone width and animation with reduced motion, and announce/refocus refused moves as well as successful ones. Only validated view state may be read from `HX-Current-URL` (`/board`, `closed=1`); it never replaces token/origin checks.
- Calendar download uses the delegated `[data-calendar-download]` helper in `app.js`: fetch a same-origin safe event URL with `X-JP-Token` in a header, save the bytes as `jobpipeline-event.ics`, revoke the object URL, and announce success/failure while restoring the button. Never put the token, event title or contact data in a URL or filename. The protected GET builds bytes through the local in-memory calendar formatter, without writes, external service/network calls or secret reads (ADR-102's explicit export exception); a normal link cannot provide the header. See `references/patterns.md`. Export downloads use the same delegated helper with `[data-file-download]` (M6, ADR-116): the protected `GET /applications/{id}/exports/{export_id}` answers only with the stored name as attachment, the fixed media type and `no-store`; the helper checks the name and type, saves a blob, announces the result and returns focus to the button. A plain link never downloads an export.
- Shortcuts are registered in `app/static/js/shortcuts.js`, listed in the `?` help, ignored while typing in inputs (and with a modifier key, or while a dialog is open), and can be switched off in settings (WCAG 2.1.4). The switch is a versioned setting (`shortcuts`, default on), shown as "Use single-key shortcuts" through `GET` and `POST /settings/shortcuts`; a stale version answers 409 inside its block with the reload prompt. The screen carries the value as `data-shortcuts="true|false"` on its root element, and `shortcuts.js` reads it. With the keys off, every action still has a visible button, and `?` still opens the help, which says how to turn them on. Each key presses the button the screen shows, so the keyboard and the mouse share one path to the server. A key that acts on a card waits for the card's "seen" answer (with a short safety release). A new screen with single-key shortcuts follows this and extends the `?` list.
- A card is marked seen by a POST sent once the card is displayed (`hx-trigger="load"`), never by a GET. The next card is prefetched by a GET to a same-origin path and marks nothing.
- Reversible actions happen at once and offer undo; confirmations are only for irreversible actions.
- Long work goes through the task runner; the button swaps to a task status fragment that refreshes on `tasks:resync` (see Live updates). The exception is one bounded page fetch whose result decides the next screen (Add job, ADR-098 item 4): it runs inside the request, with a status line (`class="htmx-indicator" role="status"`, "Fetching the page…") and the submit button disabled with `hx-disabled-elt`. A failed fetch keeps what the user typed, answers 422 with the paste-text message tied to its field, and opens the text box. See the `background-task` skill, section 4a.
- Every list and panel has its empty, loading and error states, with the copy tone from the detailed design.
- **Open editors are never replaced** (M6; ADR-114, ADR-111): a refresh skips a region while an editor, a dirty field, a modal or a request of its own is open or pending. Unsaved typing lives in page memory only (no browser storage); a restored editor keeps its original action and version. A self-refresh sends the task attempt it already shows (`X-JP-CV-Seen`), so a finished task announces once. A background task's completion is announced, not focused.

## Live updates

- Pages read `GET /events` with the small fetch-based reader in `app/static/js/app.js`. There is no `EventSource` and no htmx SSE extension (ADR-077).
- A page opts in with `{% set live_updates = true %}` before `{% extends %}`-level content renders; `base.html` then puts `data-events-url="/events"` on `<body>`. Opt in exactly on pages that include the tasks slot (every app page); guide pages never do, so they open no stream.
- The reader sends `X-JP-Token` as a header, taken from `<body hx-headers>` on every attempt. The token is never in a URL.
- It dispatches two bubbling CustomEvents on `document.body`, both with no detail: `tasks:resync` on every connection (and when a tab joins or is shown again) and `tasks:updated` for each task change. Only these two come from the stream. The server also sends `tasks:resync` in an `HX-Trigger` header after a cancel or retry (`app/api/tasks.py`). Events can arrive out of order, so a listener always refetches; never read a status from the event.
- Parts that show tasks refresh with a trigger from the body, for example `hx-trigger="tasks:resync from:body, tasks:updated from:body"` (htmx 2.0 `from:` modifier). No trigger filters, `js:` values or `hx-on*` attributes (ADR-041).
- A refreshed fragment is an ordinary GET fragment route: it needs the token and has no side effects.
- The reader reconnects by itself (backoff 1 to 30 s), pauses while the tab is hidden, shows the restart message on a 403, and shares one stream per browser between tabs (ADR-077, M2.18 update). Don't open another stream or an `EventSource`.
- `inbox:changed` (M4) is a body event too: the Add-job and "Not a duplicate" answers send it in `HX-Trigger`, and `job-detail.js` dispatches it after a change in the drawer; the inbox screen refetches its queue on it. A refresh of this kind should not swap away an open menu or typed text (the Add-job refresh does not have that guard yet: TD-242).
- Two more body events come from HTTP answers, not from the stream. `usage:changed` is sent in an `HX-Trigger-After-Settle` header by a budget save or removal, once the swap has settled; the usage panel and Testing tools refetch on it, never on `tasks:resync`. `tasks:finished` is sent in an `HX-Trigger` header by every `GET /tasks/indicator` answer, with the detail `{"tasks": [{"key", "message", "age"}]}`; app.js announces each one once and keeps its key in localStorage. Full list and refresh rules: spec 2.12 and ADR-088.

## Dialogs, blocked actions and saves

- **Modal question** (ADR-086): a native `<dialog data-modal role="dialog" aria-modal="true" aria-labelledby aria-describedby>` in a fragment, for a question that must be answered before an action starts (for example the budget warning). app.js calls `showModal()` after the swap settles, so the page behind it is inert. Initial focus goes to the safe choice (`autofocus` on "Not now"). Esc and "Not now" close it and send nothing. Tab wraps while it is open. `data-return-focus="<selector>"` names the control that gets focus back when it closes without a start. The confirmed start posts the action's own values plus the confirmation fields.
- **Never refresh a region that holds an open dialog.** A request whose own element holds an open dialog is cancelled (`htmx:beforeRequest` in app.js). A page that can change budgets refreshes its blocked actions on `usage:changed`; Testing tools refetches itself on `usage:changed`.
- **Blocked action** (ADR-086): a focusable button with `aria-disabled="true"`, not the `disabled` attribute, so keyboard users reach it and hear the reason. `aria-describedby` names the reason above it, which gives the reset date and a link to Settings. The server refuses the same start with 409, so the client guard is a convenience only.
- **Saves** (ADR-081, ADR-087): a successful save answers with a line in its block ("Saved.", or "Removed. This service has no limit now.") and moves focus to the block's heading (`tabindex="-1" data-autofocus`). The same words go to the live region through `HX-Trigger: {"announce": "..."}`. Never use `HX-Push-Url` for a settings save.
- **Partial swaps** (M6; ADR-112 item 7): a form whose answer must not wipe other unsaved text swaps only its own block (`hx-select`, plus out-of-band spots that are named in `hx-select-oob`). Its outcome line is rendered inside that block. The photo forms of Your details do this.
- **Refused and stale answers**: a refused form answers 422, with each error tied to its field (`aria-describedby`, `aria-invalid="true"`) and the first invalid field focused. A stale version answers 409 with the reload prompt, `fragments/shell/_reload_prompt.html` (`role="alert"`, the form's own explanation and a "Reload the page" link). Any form that saves to a versioned setting uses the prompt, and the 409 stays inside the form's block (ADR-081).

## Layout and accessibility

- Mobile first: layouts work from 360 px; the sidebar collapses; tables scroll inside their own container.
- A scroll container that the page can't otherwise reach is a region: `role="region" tabindex="0" aria-labelledby="<caption id>"` (see `fragments/settings/_usage_panel.html`). The e2e tests check that keyboard users can reach and scroll it, and that the page itself doesn't scroll sideways at 360 px.
- Status uses text or an icon as well as color; contrast meets WCAG 2.2 AA; targets are at least 24 by 24 px; animations respect reduced motion.
- Forms have visible labels; errors are tied to fields with `aria-describedby`.
- **Optional forms in a disclosure** (M6; ADR-112 item 2): a long optional form (Your details) is a native `<details>` under its own heading, closed in the lazy GET answer and open in every POST answer. Collapsed by default keeps the area's tab order within its tab budget (`AREA_TAB_BUDGET` in `tests/e2e/settings_areas.py`; M9.2 replaced the single 120 ceiling).
- **Refused forms keep typed values** (M6; ADR-112 item 1): a refused form refills what was typed, escaped. Error texts and logs never contain a typed value, and a refused control is tied to its fixed message.

- E2E (Playwright): the scenario at desktop and 390x844; a keyboard-only path; focus lands where intended after swaps; axe shows no serious or critical violations.
